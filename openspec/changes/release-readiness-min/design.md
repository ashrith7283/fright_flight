# Design

## Context

Observed state: `applicationId`/`namespace` are `com.example.fright_flight`; `MainActivity.kt` lives under `kotlin/com/example/fright_flight/`; the manifest label is `fright_flight`; the release build type signs with the debug config; icons are the Flutter defaults; the `INTERNET` permission appears only in debug/profile manifests (good). `pubspec.yaml` is `1.0.0+1`. No `docs/`, `ASSETS.md`, `tool/` or signing files exist. See proposal.md for motivation.

## Goals / Non-Goals

**Goals:**
- A release App Bundle that Play accepts for closed testing.
- Secrets never enter git; builds still work for a contributor without the key.

**Non-Goals:**
- Ads, Crashlytics, store graphics, `app-ads.txt`, CI, iOS.
- Creating the Play Console account or running the closed test (manual, listed as follow-up).

## Decisions

- **Package rename by hand** (edit `namespace`, `applicationId`, move `MainActivity.kt`, fix its `package` line) rather than a rename plugin: three files, fully verifiable by building and launching.
- **Icon via `flutter_launcher_icons` (dev dependency)** fed by a generated 1024px foreground and a solid sky-blue background, giving adaptive and legacy icons. The source art is produced by a small script in `tool/` using Python Pillow (or Dart if unavailable) so it is reproducible and original. Alternative: hand-edit mipmaps — rejected, error-prone.
- **Signing from `android/key.properties`**: Gradle reads it if present and creates an `upload` signing config; otherwise falls back to the debug config with a `logger.warn`. Play refuses debug-signed uploads, so the fallback cannot ship by accident, while `flutter run --release` keeps working. Alternative: fail the build when missing — rejected as it blocks routine local runs.
- **Keystore** is generated by the developer with `keytool` and stored outside the repo (and backed up); the password never passes through Claude or the repo. `docs/release.md` gives the exact command.
- **Shrinking**: set `isMinifyEnabled = true` and `isShrinkResources = true` for release with Flutter's default proguard rules; verify on a real device that audio, haptics and storage still work (plugins using reflection are the risk).
- **Obfuscation** via `flutter build appbundle --release --obfuscate --split-debug-info=<dir>` with the directory under a gitignored `build-symbols/` path (copy a backup out of the repo per release).
- **Privacy policy as Markdown in `docs/`** published by GitHub Pages (owner enables it in repo settings, Pages source `dev`/`main` `/docs`). Content reflects the no-data build; the `ads` change must update it and the Play Data safety form.
- **SDK levels**: keep `minSdk`/`targetSdk` from Flutter's defaults but verify at apply time that `minSdk >= 23` and `targetSdk` meets Play's current requirement for new apps; raise explicitly if not.

## Risks / Trade-offs

- [Package id is permanent once uploaded] → Confirmed with the developer before planning: `com.ashrith.frightflight`.
- [Lost upload keystore blocks updates] → Doc requires an off-repo backup; Play App Signing allows an upload-key reset.
- [R8 breaks a plugin in release only] → Install and play the release build on a device before upload.
- [Policy goes stale when ads arrive] → Noted in the `ads` roadmap item; policy file names the data it covers.
- [Policy publishes a contact email] → Assumption: use the developer's email; confirm before committing the policy.
- [Name "Fright Flight" may be taken on Play] → Developer checks availability in Play Console before first upload; the label is a one-line change.
